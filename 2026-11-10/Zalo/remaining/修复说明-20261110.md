## BUG-1110-01 客户级 AI 设置「应用到当前客户」后仍显示 1.6

**结论：后端持久化是好的，那次前端没有把请求发出去。**

- 复现验证：对会话 `business:0c73fa09…` 直接调
  `PUT /ai/orchestrator/conversations/{id}/assistant`（`{"assistantId":"assistant-8d74ad8b-…","modelTier":"pro"}`）
  → `204`；随后 `GET` 返回 `modelTier: "pro"`；数据库 `orch_conversation.model_tier` 由 `standard` 变 `pro`；日志有
  `AiReplyOrchestrator.java:11828 [orch] conversation … AI assistant binding -> …, modelTier=pro`。测试后已把该会话改回 `standard`。
- 测试时段（10:35–10:45）nginx 访问日志只有两次 `GET /ai/orchestrator/conversations/614678/assistant` 200
  （10:35:09、10:42:21），**没有任何 `PUT …/assistant`**，Java 日志也没有绑定记录 → 点「应用到当前客户」时请求没发出。
- 界面上的两处误导（已改）：
  1. 抽屉每次打开都回到「账号全部会话」范围，客户卡片显示的是**坐席档位**（1.6），看起来像"Pro 没保存"；
  2. 底部「应用到当前客户」只是打开二次确认弹窗，要再点弹窗里的「确认应用」才真正提交，提示不够明确。

**改动**（`frontend-user/src/pages/sessions/MetaAccountAiDrawer.tsx`）
- 记住上次使用的范围（`localStorage: acs_ai_settings_scope_v1`）；在客户范围时，打开即用该会话自己的 `assistantId / modelTier`，不再显示坐席档位。
- 客户范围确认弹窗文案改为「将把「{客服名} · {模型名}」应用到当前客户；仅修改当前客户，其他会话保持不变。」，点一次仍需第二次确认（保留防误触）。

**复验步骤**：A 会话打开 AI 设置 → 切「仅当前客户」→ 选 Pro → 点「应用到当前客户」→ 在弹窗点「确认应用」→ 出现「已应用到当前客户」→ 关闭抽屉重开，范围与模型都应保持 Pro；同一时间 `GET /assistant` 返回 `modelTier: "pro"`。

## BUG-1110-02 导出 TXT 的时间比界面早 8 小时

**根因**：`linkpilot-ai/src/main/java/com/linkpilot/ai/profile/CustomerProfileService.java` 的 `export()` 用
`ZoneId.systemDefault()` 格式化 `updated_at`，而 Java 容器时区是 UTC（`/etc/timezone = Etc/UTC`、`TZ` 未设置），
浏览器是东八区 → 导出显示 `02:50`、界面显示 `10:50`。

**改动**
- 新增 `private static final ZoneId DISPLAY_ZONE = ZoneId.of("Asia/Shanghai")` 与 `ZONE_LABEL = "（北京时间）"`；
- `export()` 改用 `DISPLAY_ZONE`，并在版本行末尾追加 `（北京时间）`；
- 同文件 `editItem()` 里「今天」的 `DAY.format(...)` 一并改用 `DISPLAY_ZONE`（原本也跟随系统时区）。

**预期输出**：`第 3 版 · 更新于 2026-11-10 10:50（北京时间）· 超管组`。
（`src/test` 内没有断言这段文案，加时区后缀不影响既有测试。）

## BUG-1110-03 群发面板显示 AI 0 / 人工 1，与实际 AI 接待不一致

**结论：不是后端数据不同步，是前端缓存。**

- 群里概览接口读的是 Java 侧 `orch_conversation.ai_enabled`；切换接管时 `OrchestratorController` 的
  `enabled=false` 分支会走 `releaseAndReply / releaseResume`，`ai_enabled` 是立即置真的（数据库已核对）。
- `frontend-user/src/pages/sessions/components/BulkSidePanel.tsx` 的概览 `useQuery` 原来 `staleTime: 15_000`，
  且只有"群发任务列表"会被 invalidate；切完 AI 立刻打开面板，15 秒内读到的还是旧概览 → 显示 AI 0 / 人工 1，
  整页刷新（清空缓存）才恢复 AI 1。

**改动**：概览改为 `staleTime: 0` + `refetchOnMount: 'always'`，每次打开面板都重新拉。

**复验步骤**：A 会话从人工切 AI → 立即打开群发面板 → AI 人数应为 1；再切回人工 → 重新打开 → 应为 AI 0 / 人工 1。

## BUG-1110-04 预约 / AI 群发显示「已发送」，客户实际没收到

**现场日志（2026-11-10 03:22:33–03:23:03Z，容器 `lp-independent-java-1`）**

| 时间 | 事件 |
|---|---|
| 03:22:33.820 | 建群发任务 `bj-4bd21e2ae9c542919b09`（mode=ai, kind=all, n=1） |
| 03:22:48.619 | `ProactiveMessageService.bulkCreate` 建闹钟 #6 |
| 03:22:51.860 | `[proactive] #6 fired … source=bulk`；`[sysevent] new turn revision=1 kind=alarm` |
| 03:22:52.4 | 投递大脑，`POST /v1/sessions/…/messages` 202 |
| 03:22:55.741 | 大脑回 `reply_final`，28 字 |
| **03:22:55.744** | **`finishSystemEvent outcome=sent`** |
| **03:22:55.774** | **`ProactiveMessageService.finish #6 sent → done`**（群发明细此时已记 sent） |
| 03:22:55.826 | 才开始打字：`[AI-REPLY] stage=TYPING … typingMs=10800` |
| 03:23:0x | 闹钟 #5（R08 单次预约）到点 → 同会话 `new turn revision=2`，第一轮发送被判无效 |
| 03:23:03 | 群发 job 收尾 `done`；全程没有该会话的发送成功日志，客户没收到 |

**根因**：`AiReplyOrchestrator.handleAgentReply()`（约 7034 行）在「AI 把文字交回来」的瞬间就
`finishSystemEvent(OUTCOME_SENT)`，而真正发送要等打字结束（约 10 秒）。这期间同会话下一条主动消息把
`revision` 推进，旧 `revision` 的发送在发送口被 `stillValid()` 判定失效直接跳过 → 任务显示已发送，客户零收到。

**改动**
1. `handleAgentReply`：只有 AI **什么都没写**（`text.isBlank()`）时才记 `silent`；写了内容则保留系统事件未收尾。
2. 发送口收尾：`speakAs(...)` 的 `ReplyPacingEngine.Outlet.textDone(int delivered)` 里调用新增的
   `finishSystemEventAfterSend(conversationId, delivered)` —— `delivered > 0` 记 `sent`；
   `delivered == 0` 记 `failed`，原因「消息没有发到客户（发送被跳过或失败）」。
   `ReplyPacingEngine` 无论成功失败都会回调 `textDone`，所以被跳过的那轮会明确落成失败，不再谎报成功。

**复验步骤**：A 保持 AI → 建一条 1 分钟后的单次预约 + 立刻建一条纯文字 AI 群发（两条同会话、时间接近）→
到点后看任务明细：真发出去的为「已发送」，被跳过的那条应为「失败 · 消息没有发到客户」，Zalo 客户端应对上。
